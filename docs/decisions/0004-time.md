# 0004: Relative time only, no wall clock

- Status: accepted; amended by [ADR 0006](0006-time-of-day.md) (the time of day picks a schedule stage)
- Date: 2026-10-08

## Context

The Pico has no battery-backed clock; wall time needs NTP, which needs the internet and DNS (which blocks the
asyncio loop). The device is switched on and off by its owner, mostly used at night, and the profile is chosen by hand.
A dependency on the time of day would be a way to stop working or to work wrongly.

## Decision

- The firmware never uses the date or the time of day. No NTP, no calendar, no time windows in rules,
  no time zone setting.
- Every duration (phases, cooldown, hard cap, manual hold, pause, min interval, confirm reads, polling) uses
  `ticks_ms`/`ticks_diff`, through one helper in the core. Ticks wrap after about 12 days; the helper and its tests
  cover that.
- The API reports seconds left or seconds ago; the web page converts them to clock times with the phone's clock.
- Flash events carry a boot counter and the uptime, not a timestamp.
- Across a reboot, elapsed time is unknown. So: an owned cycle is finished at once (ADR 0003); a pause, a cooldown
  and each rule still inside its `min_interval_min` are kept, and their timers restart from the full value (the safe
  side: a restart can delay a start, never add one). `state.json` lists those rules by name.

## Consequences

- Profile changes by time of day are manual (or a relative "profile timer" later).
- Features that need a wall clock (weather forecast, time-of-use tariffs, calendar profiles) are later, opt-in work.
- No DNS lookups anywhere: the AC is reached by IP.
